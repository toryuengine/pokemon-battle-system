### 目的
「フェーズ1の実装を開始」という依頼を受け、CLAUDE.md の「やること」C（ファクトリー本体）を進める。対象はシングル・オープンレベル。仕様書（`Battle factory gen4 rules.md`）のルールを再現し、判断はすべて Agent に聞く形にして、ランダム Agent で多数回の挑戦を回して平均連勝数を出すところまで繋ぐ。

### 実施内容
- **対戦エンジン側の小さな変更**
  - `Pokemon(..., gender=, ability_id=)` を追加。渡すと性別・特性を乱数で決めずに固定する（ファクトリーで対戦ごとに作り直しても同じ個体にするため）。性別不明は `None` なので、省略を表す値として `ROLL_GENDER` を用意した。種族が持てない特性は `ValueError`。
  - `Battle.get_usable_moves`・`Battle.get_selectable_moves` を追加。後者は状態を書き換えずに「今出せる技の一覧と、固定されているか」を返す（溜め技・げきりん→アンコール→こだわり系→制限の順。`select_move` と同じ判定）。Agent に選べる行動を見せるのに使う。`select_move` の制限の判定は `get_usable_moves` を使うようにした（動作は変えていない）。
- **`src/factory/`（新規）**
  - `rules.py`：個体値・強いポケモンの数・BP・ヒントの種類・ネジキ戦・相手の周の候補・交換できるか。周は1始まりの番号で扱う。「最も多いタイプ」の同数時の優先順は、`data/type.json` のID順ではなく第4世代の内部番号の順なので、タイプ名で対応を取る。
  - `generation.py`：`FactoryPokemon`（セット・レベル・個体値・性別・特性。`build()` で `Pokemon` を作る）。レンタル候補6体（種族・持ち物クローズ、強いポケモンは次の周のプール・個体値、並びは混ぜる）、相手チーム（第1〜6戦は今の周か1つ前の周をチーム単位で半々、第7戦は次の周、21・49戦目はネジキのプールと個体値12・31、プレイヤーと同じ種族・持ち物は除外）。
  - `hint.py`：対戦前ヒント（シングル）。
  - `observation.py`：`TurnAction`・`FactoryContext`・レンタル／並び順／交換／ターンの観測。相手は場に出てきた個体の見える情報・使った技・持ち物が変わったときに判明した元の持ち物だけ。交換は相手の種族IDだけ。
  - `battle_runner.py`：`AgentSide` がエンジンの3つの口（`switch_policy`・`move_policy`・`replacement_policy`）を Agent に繋ぐ。交代を聞かれたときに Agent に1つ選ばせ、技なら覚えておいて技選択で返す。相手の見えた情報は `Battle.events` を読み進めて集める（`OpponentKnowledge`）。引き分け・ターン上限はプレイヤーの負け。
  - `state.py`（`FactoryState`）・`challenge.py`（`FactoryChallenge`）：レンタル→相手生成・ヒント→並び順→対戦→交換→周クリアでBP・ネジキに勝てばプリント、負けたら連勝等を0に戻す（BP・プリントは残す）。
- **`src/agents/`（新規）**：`FactoryAgent`（`choose_rentals`・`choose_order`・`choose_action`・`choose_replacement`・`choose_trade`）と `RandomAgent`（`switch_chance` で交代の確率を指定可）。factory は agents を import しない（ダックタイピング）。
- **`src/experiments/evaluate.py`（新規）**：平均連勝数・周ごとのクリア率・ネジキ戦の勝率と、シード・回数・コミット（`git describe --always --dirty`）を出す。ファクトリー側と Agent 側に別々の乱数を渡す。
- **テスト**：`tests/test_factory_rules.py`（70件）・`tests/test_factory.py`（68件）・`tests/test_factory_battle.py`（41件）を追加。
  - 試行錯誤：観測のテストで「1ターン目の観測では相手の技がまだ見えていない」と書いたが、1ターン目の途中の瀕死時の交代先選びでは既に技が見えていて失敗したので、「最初の観測だけ」を確かめる形に直した。勝敗の確認の式も演算子の優先順位を間違えていたので直した。タイプの同数のテストは、最初の例（カビゴン・ハガネール）が内部番号とIDの順の違いを確かめられていなかったので、ブーバーン・カイリキー／カメックス・ベトベトンに変えた。
- `src/main.py` の結果が変更前とほぼ同じ分布（リザードン6137・引き分け1905・メガニウム1958）であることを確かめた。
- README（実装状況・本編と違う箇所・推測で決めた細かい仕様・やることリスト・「バトルファクトリー本体について」の節）と CLAUDE.md（フェーズ表・やることC、フェーズ2の項目C2）を更新した。

### 結果
- テストは全417件が通った（既存168件＋新規249件）。
- 評価（シード0・10000回、コミット 352cdfc-dirty の時点＝この変更をコミットする前の作業ツリー）:
  - `random`（行動を一様に選ぶ）：平均連勝数0.490（最大8）、1周目クリア3回（0.03%）、57.1秒
  - `random-noswitch`（交代しない）：平均連勝数1.059（最大14）、1周目クリア130回（1.3%）、2周目クリア1回、75.8秒
  - 相手もランダムに技を選ぶため1戦の勝率は5割前後。ネジキ戦まで届いた挑戦は無かった。
- 未解決：特性・持ち物が発動して判明したこと（いかく・たべのこし等）はまだ観測に入らない。相手トレーナーの行動は本編の思考ルーチンではなくランダム。仕様書に無い部分（相手の周をチーム単位で決める・ネジキ戦の前のヒント等）は推測で決めて README に書いた。
